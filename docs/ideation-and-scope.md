# AnaLoL：研究结论与候选范围

日期：2026-10-24。状态：讨论提案，不是已确认的产品规格。用户目标是灵活、有趣、可解释的 LoL 电竞分析和高性能可视化，本地运行；预测模型可参与，但不是中心。本轮只研究、审计数据和定义范围，没有实现应用或安装依赖。

## 建议定位

**AnaLoL 是一个本地 LoL 电竞研究工作台：从一个问题出发，筛选可比较的比赛，计算透明指标，通过联动图表发现差异，并追溯、保存支持结论的比赛。**

默认用户是假设中的个人研究者/深度观众，也能支持内容创作者。职业队教练的逐事件复盘需求不是当前数据可以完整覆盖的。无商业化要求时，价值标准应是“是否让人更容易提出、检验和表达有趣的问题”。

最小工作循环：

```text
问题 → 样本与比较基准 → 指标与联动图表 → 具体比赛证据 → 保存分析
                         ↑                         │
                         └────── 修改假设 ──────────┘
```

“框架”体现在数据和计算可以被不同视图、报告及 notebook 复用，不需要先实现插件系统、任意布局引擎或自定义公式语言。

## 从已有工具学什么

完整先例研究见 [金融与体育分析先例](research-analysis-precedents.md)。这些是有实际文档和源码的成熟模式，未验证其商业成功或本机速度。

| 先例 | 可以借鉴的模式 | AnaLoL 中的落点 |
| --- | --- | --- |
| [QuantStats](https://github.com/ranaroussi/quantstats) | 指标、图表、报告分层；benchmark 对照；本地 HTML 报告 | 同一组指标同时支持交互探索和选手/战队分析报告 |
| [vectorbt](https://vectorbt.dev/) | notebook/浏览器中的快速参数和样本比较 | 快速切换版本窗口、队伍、英雄、对手条件，保留比较状态 |
| [kloppy](https://kloppy.pysport.org/) 与 [mplsoccer](https://mplsoccer.readthedocs.io/en/latest/) | 一致数据语义与可复用的领域图表 | 先明确比赛/玩家/战队粒度，再提供少量适合 LoL 的图表 |
| [socceraction / VAEP](https://socceraction.readthedocs.io/en/latest/documentation/valuing_actions/vaep.html) | 预测模型成为动作价值的测量工具 | 将来研究局势价值；需要事件数据，不是现在的默认能力 |
| [Games of Legends](https://gol.gg/players/list/season-S16/split-ALL/tournament-ALL/) | 可按赛季、赛事、位置筛选常见职业指标 | 基础数据查阅的参照；AnaLoL 可以着重自由样本比较、图表联动和分析可复现 |

金融领域应迁移的是 benchmark、分布、稳定性、研究工作流，不能因存在时间轴就机械引入 RSI、MACD、K 线或“买卖信号”。LoL 比赛不是连续、同分布的市场价格序列；补丁、阵容和对手会改变统计含义。

## 数据决定的边界

见 [本地数据审计](data-audit.md)。四份 CSV 共 41,112 个不同 gameid、493,344 行、165 个字段。每小局包含 10 个玩家行和 2 个战队行；它们不是 12 场独立比赛。

当前适合：赛后表现、固定时间快照、风格分布、资源分配、条件胜率、英雄使用和部分选禁趋势。

需要补充数据才适合：地图控制、游走/打野路径、团战分段、装备成型时刻、连续比赛状态、每次目标置换和逐动作价值。

特别限制：

- 本地 2023–2025 LPL 的 GD@15 全缺失；2026 LPL 约 80.4% 的战队行可用。2026 LCK 在这个字段上完整，适合作为第一条演示流程的样本。
- 没有可靠显式 series_id，也没有经过验证的系列赛 BP 历史。Fearless 的英雄可用集合取决于赛制、局序和前局选用，不应拿全赛事 ban/pick 比率冒充可用时选择偏好。
- 结果表存在双方都记为未获胜的短局；先隔离异常，不擅自推测胜者。complete 标记不能代替字段级检查。
- 新旧赛季目标不同、身份 ID 有缺失、字段 year 与日历年可能不同。这些必须保留语义。

Riot 的官方电竞数据页面目前将 LoL 数据分发指向 GRID，并引导联系获取访问；它不是一个已验证能免费补齐所有历史赛事轨迹的承诺。[Riot 官方数据产品](https://riotesportsdata.com/en-us/product-overview/) 标准 Riot API 和 Data Dragon 各有自己的用途，不能默认一个普通 API key 就拥有职业赛事完整遥测；英雄静态资料可参考 [Riot 开发者文档](https://developer.riotgames.com/docs/lol#data-dragon)。

## 三个值得探索的产品方向

| 方向 | 用户会回来做什么 | 当前可行性 | 取舍 |
| --- | --- | --- | --- |
| 风格与表现研究 | 比较选手、资源分工、战队前期表现和版本前后变化 | 高；缺失需要显式处理 | 建议作为核心，问题多，少量图表可复用 |
| Meta / BP 实验室 | 观察英雄优先级、赛区偏好、英雄池变化 | 基础趋势可做；精确 BP、Fearless 解释需要额外验证 | V1 放基础热图；完整模拟器后置 |
| 比赛故事与战术复盘 | 观察局势拐点、移动、视野、团战决策 | 当前只有稀疏快照和终局统计 | 最具空间表现力，但依赖新数据，应作为独立扩展 |

建议核心选第一个，吸收第二个的基础趋势。不要把三条方向各自做成完整产品。

## V0：先验证一条真实分析流程

**参考问题：2026 LCK 同位置选手的资源与输出关系有什么不同，这种差异是否只是英雄构成或少数比赛造成的？**

一个研究页面足够：

1. 选择联赛、时间/补丁窗口、位置；默认 2026 LCK bot，允许换成其他位置。
2. 显示每名选手的平均 earned-gold share 与 damage share 散点，样本量明确；两个 share 的口径分别展示，不称为投资回报或纯实力。
3. 点击选手或框选一组点，联动英雄构成、逐场分布和比赛表；比较组可固定为 A/B。
4. 点一场比赛，打开 10 人对照表和可用的 10/15/20/25 分钟快照，保留缺失。
5. 保存筛选条件、指标、比较组、数据快照标识；导出一张图及其底层数据。

这是一个纵向闭环，不是先铺五六页静态 dashboard。通过它验证计算复用、图表联动、解释性和交互速度后，再扩展视图。

## V1：候选范围

### 一套共享研究状态

- 本地读取四年数据；用户可筛选联赛、日期/补丁、阶段、红蓝方、队伍、选手、位置和英雄。默认同联赛、同位置、相近补丁窗口比较，跨赛区比较显式提示基准差异。
- A/B 两组样本与一个明确的参考群体；支持多个实体同图比较。
- 表格和图表共用同一批比赛；点击/框选能追溯和反向筛选。
- 保存命名分析，不做账号系统。保存状态包含输入快照、筛选、指标口径、比较基准和视图设置。

### 三种有明确问题的视图

| 视图 | 主问题 | 默认图形 | 点击后的证据 |
| --- | --- | --- | --- |
| Player Explorer | 他拿了多少资源、如何输出、对线表现是否稳定？ | 资源—输出散点、GD@15 分布、角色分位点图、英雄构成 | 每场表现、对手、英雄、红蓝方、原始统计 |
| Team Compare | 前期领先分布、资源分工、目标获取和节奏如何不同？ | GD 快照小多图、五位置资源分配、目标占比、条件胜率分箱 | 构成样本的比赛与快照；不伪造连续过程 |
| Meta Explorer | 英雄选择和禁用如何随补丁/赛区变化？ | 英雄×补丁热图，pick 与 ban 分开，标样本量 | 选用队伍、对手、位置和具体比赛 |

少量默认报告可直接使用这些视图。图表配置可换轴、换指标和基准，不需要任意拖拽布局。雷达图可选，不作为默认唯一画像：分布和分位点更容易暴露不稳定与小样本。

### 首批指标：少而明确

| 指标族 | 起步指标 | 解释边界 |
| --- | --- | --- |
| 对线/早期 | GD@15、CSD@15、XPD@15、GD@10/20/25 作为可选快照 | 含英雄、对手、队友影响，不能直接称为个人对线实力 |
| 资源分配 | earned-gold share、各位置资源占比、10→15 分钟经济增量 | 区分 earned gold 与 total gold；不能混用分子分母 |
| 输出与参与 | DPM、damage share、KP、死亡/分钟 | KP 在 teamkills=0 时不可定义；高伤害未必高贡献；位置不可无条件混比 |
| 战队局面 | GD@15 分布、领先/落后样本的获胜率、比赛时长分布 | 条件胜率按领先幅度和样本量展示；受对手和阵容混杂，不直接叫运营能力 |
| 目标与 Meta | 小龙/大龙份额、首塔率、pick rate、ban rate | 用 team 行；目标只统计适用版本；BP 分母用可观测的完整记录 |

范围是上述少量字段和派生计算，不是一次上线所有组合。每个指标必须有粒度、公式/源字段、单位、比较基准、有效样本量、缺失处理与方向含义。派生 share/ratio 应明确是“逐场先算再平均”还是“先汇总再相除”。两种值不能同名混用。

KP 的逐场定义为 `(kills + assists) / teamkills`，零分母保留未定义；滚动统计按时间顺序、固定局数或时间窗口，并明确补丁/阵容边界。比率给适当区间或低样本提示；同一局两队以及同系列赛比赛不作为完全独立样本来夸大精度。没有可靠系列赛标识时，先标为粗略不确定性，不报告虚假的精确显著性。

### 有趣来自可检验的问题

- 看起来“低资源高输出”的 ADC，换成同英雄、相近补丁比较后还成立吗？
- 某队平均 GD@15 很高，是每场都领先，还是几场大胜拉高均值？
- 一支队伍在相近领先幅度下最终赢了多少场？它和“经常先拿领先”的队伍是同一批吗？
- 同一选手近期 GD@15 变化，是否伴随英雄、对手、红蓝方或阵容变化？
- 某个英雄的赛事选择热度上升，集中在哪些队伍/赛区？小样本胜率是否夸大了观感？
- 检索“GD@15 < -2000 且最终取胜”的比赛，作为后续看录像的素材，而不是凭汇总表解释逆转机制。

## 模型的合适位置

**先做好描述和比较，再将模型作为可选的测量工具。**

1. 初步可用角色/英雄/补丁基准的表现偏离，之后才考虑透明的回归基线；输出是残差和不确定性，不是“真实实力”。样本不足时退回更宽基准，而不是拟合每个稀疏组合。
2. 可探索选手或战队风格聚类，但原始指标必须可见；一开始用可解释散点就足够，不必先做 UMAP 嵌入。
3. 稀疏快照最多支持固定时刻的局势概率研究。连续 WP、WPA 或决策价值需要更细数据；状态变化也不是某个动作的因果价值。

三个有价值的阅读入口：

- [Riot：Win Probability 开发日志](https://lolesports.com/en-GB/news/dev-diary-win-probability-powered-by-aws-at-worlds)：2023 年的实现说明，使用局内经济、经验、存活人数与目标状态等信息，服务于局势叙事。说明模型能支持可视化；其特征不能从本地 CSV 全部复现。
- [SIDO Performance Model](https://arxiv.org/html/2403.04873v2)：将表现放在自己、队友、对手的背景中，评估指标的区分度、独立性和稳定性。主要研究的是高分段 solo queue 数据；职业队固定阵容会使个人与队友影响难以分离，不能照搬为职业赛因果评分。
- [PandaSkill](https://arxiv.org/html/2501.10049v2)：按位置估计单场表现，再更新技能评分，并处理区域评分池差异。启发是区分“某场发挥”和“长期水平”；论文结果不等于当前数据上的已验证效果。

若之后增加赛前预测，严格按时间切分、按系列赛分组，并只用预测时刻已知的数据；终局统计不能作为赛前特征。模型解释工具本身不提供反事实或决策建议的有效性保证。

## 本地形态与性能

无需租服务器。候选首版可以是本地 Python 进程提供浏览器界面，计算和数据都在本机；只监听本地地址。这里的 localhost 服务不涉及公共部署。notebook 作为高级分析入口可后置，核心计算保持可直接调用。

推荐先验证 **Python + DuckDB + 本地列式缓存 + Dash/Plotly** 的小方案，而不是立即选择桌面壳或自研前端。原始 CSV 保留不动，缓存可再生成；DuckDB 文件或 Parquet 选一种满足需要的主要分析存储，不必建立两份完整事实库。React/原生壳是否值得，等关键交互原型验证后决定。

[DuckDB 对 Parquet 的列裁剪和过滤下推](https://duckdb.org/docs/lts/data/parquet/overview) 适合选择少量字段、筛选和聚合的读取模式。[Dash 浏览器端回调](https://dash.plotly.com/clientside-callbacks) 可以用于已有数据上的轻量交互；数据库查询仍留在本地计算进程。[Plotly 性能文档](https://plotly.com/python/performance/) 给出 typed arrays、WebGL 与大数据聚合路径，同时说明 WebGL 的硬件和上下文限制。

当前只有约 49 万行，其中不同比赛约 4 万局，性能首先取决于是否每次重读 CSV、重复计算与传送全部原始数据，不应直接定义为 GPU 工程。

候选体验目标（不是实测或承诺）：

- 热缓存下常见筛选到完整视图更新，p95 约 500ms 以内；在明确的参考机器、固定数据快照和查询集合上测量。
- 已加载点集的 hover/选中反馈即时；纯视觉操作不重新执行全量计算。
- 大型原始表分页/虚拟化；概览聚合，选择后再加载逐局细节。
- 冷启动与首次导入单独计时；原始文件变化后显式刷新缓存，不在每次交互里探测或重建。

## 首版明确不做

公共部署、登录/权限/订阅、多人协作、实时比分与下注、自动爬取全网数据、SoloQ 综合工具、BP 推荐/模拟器、逐动作评分、地图复盘、任意仪表盘搭建器、指标脚本语言、通用插件市场、自动训练平台。

这些是本轮范围取舍，不能据此删除未来数据所需的来源和语义。将来增加一个新指标，理想上只是新增一个普通计算和定义，复用已有选择/图表/报告，不需要修改所有页面。

## 验收与下一步

V0 的验收是：可以完整走通上述 LCK 选手研究，切换比较样本、看到分布和样本量、追溯原始比赛、保存再打开同一份分析；所有值来自同一计算口径。抽取具体比赛人工复核，另核查分母为零、缺失、重复计数和异常赛果。

V1 的验收是：相同机制能够回答选手资源—产出、战队前期分布与领先样本结果、英雄使用随补丁变化这三类问题，而不是只增加页面数。

当前最值得先决定的是主要使用场景：更偏个人自由研究、战队/选手观察，还是 Meta/BP 研究。没有额外偏好时，按“个人研究工作台，以选手/战队风格为主”推进。

未检查：官方数据源的访问价格与授权、全部字段语义、框架在本机的实际性能；未训练模型。
主要风险：样本偏差和覆盖差异可能被漂亮图形放大；汇总数据不能证明战术机制、个人因果贡献或某个决策的优劣。
